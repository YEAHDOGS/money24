## Part A — Nine-topic review

### 1. Architecture

- **A §2, “four planes”; A §7, “Control plane.”** This is already five storage systems plus two MCP servers, multiple brokers, multiple model transports, and a second execution implementation for cloud-only users. That is excessive before one reliable order round trip exists. Make v1 one Go runner, local SQLite, one Webull account, one data adapter, and a read-only Svelte monitor. Add D1 for account/configuration and a DO relay when remote monitoring is actually needed. Defer KV, archive conversion, shared quote distribution, cloud trading and remote order tools.
- **A §5, “Works offline and catches up.”** Offline autonomy and remote control have conflicting authority. A laptop and VPS can both run the same account; neither a WebSocket nor a heartbeat prevents double execution. Specify one active executor per account, a durable executor identity/epoch, explicit handoff, and fail-closed recovery. Do not automatically promote a replacement while an old runner may still trade. A cloud lease cannot fence a partitioned runner at Webull unless the broker can enforce it; for v1, prohibit automatic failover and require reconciliation/manual handoff.
- **A §3, “one static binary”; “~20–50 MB RAM”; “~1,500 lines.”** These are unsupported sizing promises. Tray libraries can introduce CGO; model CLIs consume additional memory. Remove the RAM and line-count claims. Record Go as the proposed engine exception under the brief's authorization, with implementation gated on the repository rule amendment. Measure RSS, CPU, cold start and packaging on the actual dependency set. Rust remains part of the Tauri shell even if no custom Rust trading logic is written.

### 2. Pros / cons

- **A §12, “Webull Go client must be hand-written.”** Incorrect as a blanket claim: a community SDK and official Go CLI exist; official supported SDK documentation still lists Python/Java. Replace with “evaluate and pin an existing Go implementation; Money 24 owns compatibility and recovery verification.” See B1.
- **A §12, “our DB stays tiny”; A §8, “~4 migrations ever.”** Neither follows from broker custody or JSON. Reconstructing P&L needs fills, fees, instrument multipliers, cash movements and corporate actions; schema versions and indexes evolve regardless of JSON. Remove both promises. Define retention and storage estimates from measured event volumes.
- **A §12, “Keys ... stay on the user's machine.”** Local CLIs, plugins and subprocesses can access files and environment variables. This is a threat boundary to design, not a security guarantee. Isolate model processes from broker credentials; expose narrow intent tools; use OS credential storage and redacted logs. Document supply-chain updates and local malware as residual risks.

### 3. Goals

- **A §1, “multi-asset ... on Webull's API sandbox.”** This reads as established sandbox parity across six asset classes. It is not demonstrated. Replace with a capability matrix by region, account, environment, instrument and order type, each carrying a tested date. First milestone: one US equity/ETF paper strategy. Options expiry/assignment, futures rolls, crypto and event settlement are separate projects.
- **A §1, “$0/month”; A §16, “Build phase total: $0/mo.”** This can describe incremental DOGS hosting spend, not the system's total cost. Existing subscriptions, electricity, a running computer, market-data licences and API consumption are real costs. State prerequisites and distinguish company, developer and end-user bills.
- **A §18, “90-day paper record per strategy.”** Duration alone does not establish edge or safety. Require out-of-sample results after spread/slippage/fees, appropriate benchmarks, drawdown and exposure reporting, and enough relevant trades. Define deployment safety independently from profitability; a profitable backtest does not excuse unreconciled orders.
- **D §1, “Harvest”; D §2, “Show the thinking.”** The metaphor hides basic financial concepts. Use “Realized P&L” and “Emergency stop” as primary labels, with metaphor secondary. Show decision summaries, inputs, timestamps, risk verdicts and actual tool actions; do not promise access to private model reasoning.

### 4. Bottlenecks

- **A §4, “Both are possible”; A §6, “<1,500 calls/day.”** Thirty scheduled roles are not thirty predictable inference calls: tool turns, debates, retries and context replay multiply work. Use bounded concurrency, per-provider queues, jittered schedules, event coalescing, single-flight runs, deadlines, and hard reservations against token/dollar budgets. On throttling, stop new intents while deterministic protection continues. The feasibility claim must wait for a measured seven-day workload.
- **A §6, “cents/day.”** False for the researched current Grok prices at the proposed workload. At 1,500 calls/day, 3,000 input and 500 output tokens each, Grok 4.3 is approximately $7.50/day before tools/retries. See B4. Publish cost per role and per completed decision, not one blended token figure.
- **A §10, “every 15 s”; A §7, “~1–5 ... users.”** A runner emits 5,760 heartbeats/day; five emit 28,800 before loops, UI traffic or sync. This is message volume, not automatically billable request count: calculate using current provider metering rather than equating the two. Specify payload size, persistence frequency, fan-out, indexes and archive operations before claiming free-tier capacity. Avoid storing every heartbeat.
- **A §4, “ms–1 s.”** A local risk evaluation is not a guaranteed broker acknowledgement or fill. Set separate measured budgets for snapshot age, local evaluation, submission, acknowledgement and reconciliation. Track event time and receive time; discard stale intents and halt on stale or gapped feeds.

### 5. Issues and safety

- **D §1, “Frost ... cancels open orders”; D §2, “one tap away.”** Cancelling every order may remove protective stops while leaving positions open. Define separate actions: stop new entries, cancel entry orders, preserve/verify protective exits, and explicitly authorized flattening. Show requested, runner-acknowledged, broker-confirmed and failed states. An offline phone cannot guarantee a cancellation; display last confirmation and broker contact/manual action guidance.
- **A §5, “Written before submission.”** Necessary but insufficient. Persist an intent ID and client order ID transactionally before sending; reserve account-level exposure atomically across gardens. A timeout means UNKNOWN, never permission to resubmit with a new ID. Query/reconcile before retry. Track partial fills, cancel/replace races, rejected exits, manual broker trades and reconnect duplicates. Emergency handling must remain available during model or billing failure.
- **A §9, “only the Trader role can emit an intent.”** A role label is not authorization. Enforce account/garden scopes in the runner and tie approvals to an immutable order payload, snapshot version and expiry. Validate tool parameters independently of model text. Local HTTP requires authenticated pairing, strict origin/host checks and bounded requests; localhost is not an authentication mechanism.
- **A §11, “No regulatory issue beyond broker terms.”** Delete this categorical legal conclusion. Paper-only operation still has data licences, privacy obligations and potentially promotional/advice implications. Country- and product-specific legal clearance remains **UNVERIFIED**; do not imply that a disclaimer or the phrase “user-controlled software” resolves it.
- **D §§3, 5, 7.** Rolling prices, animated cards and forced single-screen layouts can impede timely reading and accessibility. Freeze sorting while a user inspects an order, reserve card space, provide a no-motion mode, and keep critical controls reachable with zoom and large text. At 320×320 prioritize mode, stale/offline state, positions and emergency control; do not reduce the view to a reassuring profit number. The current one-screen rule needs an explicit accessibility accommodation if zoom makes scrolling necessary.

### 6. Payments

- **A §15, “Recommended at launch”; “Fallback if Creem rejects.”** Processor acceptance for this exact product is **UNVERIFIED**. A cheaper published fee is irrelevant if underwriting rejects autonomous trading software. Make written product acceptance, reserve/payout terms, refunds and dispute treatment prerequisites to selecting a provider. This review does not revalidate the draft's fee schedule.
- **A §15, “Avoid: sell on the web, unlock mobile.”** That is not a universal store-policy exemption. Replace with a region/store/distribution decision and approval check before shipping purchases or external checkout links. Keep sideloaded Android and store distribution distinct.
- **A §15, “entitlements ... webhook into D1.”** Add signature verification, replay protection, unique event IDs, out-of-order event reconciliation and explicit expiry/grace states. A subscription lapse must not disable protective risk checks, emergency cancellation, position visibility or data export. Paid permission can block new strategies; it must not abandon existing exposure.
- **A §15, paid desktop/MCP tiers; A §6, subscription bridge.** OpenAI's current SIWC terms prohibit requiring payment to use that integration. Rework tier boundaries before implementing it. Defer USDC/x402 and annual-only defaults until one accepted payment flow works. See B3.

### 7. Side services

- **A §16, Sentry + PostHog + Cloudflare analytics + multiple alert channels.** Too many integrations for the first strategy. Start with structured local logs, one error sink with credential/account redaction, and one opt-in alert channel. Do not put broker payloads, prompts or balances into analytics by default.
- **A §16, “Email Routing (inbound).”** An inbound service does not deliver recovery emails. Name a transactional sender or keep initial authentication genuinely email-independent with recovery codes and documented lost-device recovery. Verify passkey storage/recovery and step-up behavior before naming Better Auth as a completed design.
- **A §10, “DO marks ... offline ... and alerts.”** A hibernating object needs an explicit scheduled check/alarm or external monitor; absence of traffic does not execute code. Monitor the watchdog itself and define delayed/deduplicated notifications. A free push channel is not a delivery SLA.
- **D §6, tray, startup and keep-awake.** Put these in the Tauri host, not duplicated Go GUI packages. Specify close-window versus quit-runner semantics, crash recovery, update behavior while armed, and a single-instance lock. An update must not restart an armed engine invisibly.

### 8. Subscriptions needed

- **A §§13, 16, data prices.** Separate terminal subscriptions from OpenAPI non-display subscriptions and from external display/redistribution rights. A $99 retail data plan is not proof of a SaaS distribution licence. Each required feed must have a verified entitlement, payer, allowed consumers, retention rights and renewal/failure behavior. Exact Webull prices remain **UNVERIFIED** here; see B2.
- **A §§6, 16, “user's own keys / CLIs.”** API billing and consumer subscriptions are distinct products with provider-specific integration rules. Maintain separate adapters and state: API-key billing, approved subscription integration, local CLI and local model. Do not offer an unverified fallback or rotate accounts to evade limits.
- **A §16, “~$35–65/mo.”** Remove the unsupported total. It omits or mixes end-user inference/data, legal work, signing, monitoring, tax and VPS costs. Provide an assumptions-based launch worksheet later, with unknowns left blank rather than priced at zero.

### 9. Systems and data contracts

- **A §8, “same docs shape.”** Configuration documents are fine; financial execution needs explicit durable constraints. Use SQL migrations for orders, fills, cash movements, exposure reservations and inbox/outbox IDs; JSON for provider payloads and strategy configuration. Define integer units or exact decimal strings, currency, tick size, lot size, multiplier, timezone/session and schema version. Never use binary floating point for money or silently coerce derivatives into equity quantities.
- **A §§2, 8, “broker ... source of truth.”** Broker truth covers its executions/custody; local truth covers commands and decisions. State who owns configuration versions and sync conflicts. Persist idempotent outbox/inbox events, ordering/cursors, retention and replay rules. DO, D1 and local SQLite cannot all be primary for the same record.
- **A §8, “hash-chained”; D §4, “Hash-chain check mark.”** A writable local chain can be rewritten in full. Describe it as integrity checking unless roots are anchored independently and rollback/deletion detection is specified. Add restore drills, disk-full behavior, backup encryption and recovery reconciliation before a reassuring badge.
- **D §4, “Approved/Vetoed → Filled → Closed.”** This collapses decisions, orders and positions into a misleading linear state machine. Separate intent approval from broker state. Add submitted, acknowledged, partially filled, cancel-pending, cancelled, expired, rejected and unknown/reconciling. A vetoed intent never becomes a fill; a filled order is not a closed position.
- **A §18, “24 h without manual help.”** Add fault-injection exit tests: drop the submission response after broker acceptance; restart between persistence and send; duplicate/reorder events; disconnect while cancelling; expire model/data tokens; fill the disk; suspend/resume; start two runners. Passing a happy-path soak is not evidence of safe recovery.

## Part B — Live research

### B1. Webull and Go

**SDK status.** Webull's supported SDK page lists Python and Java, not a supported Go SDK. However, Webull publishes a Go CLI with official signing code under `internal/auth`; that internal package is not an importable public SDK contract. A community OpenAPI SDK exists at `github.com/sfreiberg/webull` and documents signing and an API compatibility matrix. This is different from legacy clients that reverse-engineer the retail app. Community maintenance, full asset coverage and production suitability remain **UNVERIFIED**; inspect the matrix, licence, release history and recovery behavior before adoption. Sources: [official SDKs](https://developer.webull.com/apis/docs/sdk/), [official CLI](https://github.com/webull-inc/webull-openapi-cli), [community SDK](https://github.com/sfreiberg/webull).

**The trade-event protos are published.** Live GitHub tree inspection found these exact source paths:

- [Python `webull/trade/events/events.proto`](https://github.com/webull-inc/webull-openapi-python-sdk/blob/HEAD/webull/trade/events/events.proto).
- [Java `webull-openapi-java-sdk/src/main/resources/proto/events.proto`](https://github.com/webull-inc/webull-openapi-java-sdk/blob/HEAD/webull-openapi-java-sdk/src/main/resources/proto/events.proto).
- Quote wire format: [Python `webull/data/quotes/subscribe/message.proto`](https://github.com/webull-inc/webull-openapi-python-sdk/blob/HEAD/webull/data/quotes/subscribe/message.proto).

The event schema declares `grpc.trade.event.EventService.Subscribe`, a server-streaming RPC. The envelope includes a payload string: generating Go protobuf bindings does not automatically decode all business events. Implement payload validation, authentication failures, subscription expiry, ping handling and reconnect/reconciliation. Pin upstream commits before generation; HEAD links here identify inspected paths, not immutable release dependencies.

**Exact REST signing reference.** The [official signature specification](https://developer.webull.com/apis/docs/authentication/signature/) documents HMAC-SHA1: combine query parameters with the six signing headers (`host`, app key, timestamp, nonce, algorithm and signature version), sort by name, join `key=value` pairs with `&`, prefix the path and `&`, append the uppercase MD5 hex of the exact compact body when present, percent-encode the complete result, then Base64-encode HMAC-SHA1 using `app_secret + "&"` as key. Do not include `x-signature` or `x-version` in that canonical string. The page supplies a worked test vector. Hash the same bytes actually transmitted; test spaces, Unicode, empty bodies and duplicate query keys.

**There is a real documentation/version discrepancy.** Current [Python composer source](https://github.com/webull-inc/webull-openapi-python-sdk/blob/HEAD/webull/core/auth/composer/default_signature_composer.py) selects HMAC-SHA256 and uppercase SHA256 body hashing. Its [algorithm implementation](https://github.com/webull-inc/webull-openapi-python-sdk/blob/HEAD/webull/core/auth/algorithm/sha_hmac256_new.py) Base64-encodes the HMAC digest. The [official Go CLI signer](https://github.com/webull-inc/webull-openapi-cli/blob/HEAD/internal/auth/signer.go) supports SHA1/MD5 and SHA256/SHA256, defaulting to SHA1. Do not claim one algorithm is universally required or port only a blog example. Pin the selected implementation and verify accepted algorithm/version against sandbox.

**gRPC signing is not REST signing pasted onto metadata.** The [official event composer](https://github.com/webull-inc/webull-openapi-python-sdk/blob/HEAD/webull/trade/events/signature_composer.py) hashes serialized protobuf bytes, supplies signing metadata without REST host/path, and reuses the no-path canonicalization branch. That branch joins sorted pairs with `=` instead of REST's `&`; body digest case also differs from REST in the inspected code. Capture cross-language golden fixtures. A conventional gRPC credential interceptor alone does not establish compatibility.

**Effort estimate — engineering judgment, not vendor guidance.** For one experienced Go engineer with working API approval and entitlements: REST signing plus accounts/orders and fixtures, 2–4 working days; MQTT auth, payload decoding, resubscribe and bounded fan-out, 3–5 days; generated gRPC client, metadata signing, expiry/reconnect and event decoding, 2–4 days. Add 5–10 days for order-state reconciliation, unknown submissions, adversarial transport tests and a sustained paper soak. Roughly 3–5 engineer-weeks for a narrow reliable adapter, excluding approval delays, derivatives, packaging and legal/licensing. Existing code can shorten plumbing, not eliminate verification. A 2–3-day happy-path spike is plausible; “1,500 lines” is not a delivery estimate. Go helps deployment and concurrency; it does not remove broker or LLM network latency.

### B5. Go libraries and Tauri 2 sidecars

**MQTT 3.1.1:** use `github.com/eclipse/paho.mqtt.golang`, whose [package documentation](https://pkg.go.dev/github.com/eclipse/paho.mqtt.golang) explicitly supports that protocol and TCP/TLS/WebSockets. Do not accidentally substitute the separate MQTT 5 library. Configure protocol version, TLS, reconnect/backoff, bounded callbacks and explicit resubscription. Paho transport recovery is not quote-gap recovery: request a fresh snapshot and withhold new intents until state is current. Never let a blocked quote consumer stall the risk/event path.

**gRPC:** use `google.golang.org/grpc` and `google.golang.org/protobuf`; generate with `protoc-gen-go` and `protoc-gen-go-grpc` per the [official Go quickstart](https://grpc.io/docs/languages/go/quickstart/). Specify Go package mappings when upstream protos lack `go_package`. Add TLS, signed metadata, stream cancellation, deadlines on unary calls, and broker-specific reconnect rules. Successful transport reconnect does not replay missed fills; reconcile REST state before permitting new orders.

**Pure-Go SQLite:** `modernc.org/sqlite` is a CGO-free `database/sql` driver. Its [maintainer documentation](https://pkg.go.dev/modernc.org/sqlite) explicitly warns to match the `modernc.org/libc` version used by its own go.mod and lists supported OS/architecture pairs. Windows amd64/arm64 and macOS amd64/arm64 are listed; do not infer Android support from Linux. Pin versions and build all selected desktop targets. Operational choices: local disk only, WAL, bounded busy timeout, short writes, one controlled writer, migrations embedded from versioned SQL, backup via a consistent SQLite mechanism, and explicit disk-full/corruption recovery. CGO-free does not mean dependency-free or encrypted at rest.

**Tray:** prefer Tauri's [built-in system tray](https://v2.tauri.app/learn/system-tray/) in the existing native host. A Go alternative is [getlantern/systray](https://github.com/getlantern/systray), but its own README requires CGO, weakening the single cross-compiled static-binary story. Avoid two tray/event-loop owners. A standalone headless VPS build needs neither.

**Keep awake:** implement a small OS-specific host integration rather than assuming a cross-platform package solves availability. Windows offers [SetThreadExecutionState](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-setthreadexecutionstate); use an idle-system assertion, not a forced always-lit display. It is thread-scoped, so a direct Go binding must hold a locked OS thread for assertion/cleanup. The API cannot prevent all user-initiated sleep. On macOS, evaluate an IOKit power assertion in the native host or a supervised `/usr/bin/caffeinate` helper tied to engine lifetime; exact chosen flags and lid/battery behavior remain **UNVERIFIED by runtime testing**. Release assertions when disarmed and after failures. Sleep prevention is never a substitute for broker-native protection and resume reconciliation.

**Desktop packaging:** Tauri's [external-binary guide](https://v2.tauri.app/develop/sidecar/) requires target-triple-suffixed binaries and `externalBin` configuration. Build Go per matching OS/architecture; include `.exe` on Windows. Grant only the exact sidecar and fixed allowed arguments, never arbitrary shell commands from model/UI text. Use framed stdio or authenticated local IPC, redact output and handle child exit. Define one owner for process lifetime and reap children on quit. Validate Windows hidden-process behavior, executable signing and macOS signing/notarization of the nested binary; test installed packages, not just `go run`.

**Android:** Tauri's [shell plugin platform matrix](https://v2.tauri.app/plugin/shell/) supports only opening URLs on Android/iOS, not desktop-style child-process execution. The current Android companion decision is therefore necessary for both packaging and background-execution reasons. Do not bundle `m24d` as if Android were another desktop sidecar target. A native embedded Go/JNI/background-service design would be a separate product project and still would not guarantee 24/7 phone execution.
